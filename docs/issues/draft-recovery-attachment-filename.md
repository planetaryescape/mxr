# Keep the original attachment name through legacy recovery

The S05b real-HTTP recovery probe against published v0.6.86 preserved the exact attachment bytes after a failed save, retry and daemon restart, but the recovered legacy raw-path attachment name included UUID prefixes. Its provider witness matched all 432,000 bytes (`c8d8d2b24bf66a43689763d57906e1fdb43b45168342687f594f7354592a9cd2`); the prefixed name is visible in the [published recovery receipt](../build-log/daemon-portability/evidence/s05b-installed-v0.6.86/http-recovery-acceptance.json). The earlier candidate `140225cd27c7dd143d4ed987b5efce1562d9e3dd` showed the same behavior.

This behavior is outside the new managed-resource upload path. In published source `b651ee69ae01a1e08ecc021fa8d7767aa68cf12f`, `copy_recovery_attachments` copies bridge-owned uploads and replaces the attachment path with the copied path ([`crates/web/src/lib.rs#L3341-L3388`](https://github.com/planetaryescape/mxr/blob/b651ee69ae01a1e08ecc021fa8d7767aa68cf12f/crates/web/src/lib.rs#L3341-L3388)). The `compose_attachment_path` helper prepends a UUID to each copied filename ([`#L3545-L3548`](https://github.com/planetaryescape/mxr/blob/b651ee69ae01a1e08ecc021fa8d7767aa68cf12f/crates/web/src/lib.rs#L3545-L3548)). The function is unchanged from base `74a151c5c41d2d3f6b780fdbeb92c74db535ab57` ([`#L3155-L3202`](https://github.com/planetaryescape/mxr/blob/74a151c5c41d2d3f6b780fdbeb92c74db535ab57/crates/web/src/lib.rs#L3155-L3202)).

Follow up separately on preserving the user's display filename while retaining collision-safe private paths. This is nonblocking for S05b: published bytes, content hash and provider delivery passed.
