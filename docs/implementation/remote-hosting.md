# Remote access ships as usable client journeys

Status: F01 released and accepted in v0.6.94; R1 building. Updated 2026-10-12. Canonical feature contract: [blueprint 24](../blueprint/24-remote-hosting-and-clients.md). F01 base: `origin/main` `bf66f451ac1d6ac9463290844926c9626a942cea`, fetched before review. The source blueprint's R01a–g describe component ownership; this ladder supersedes their execution order without dropping their acceptance requirements.

One authoritative Mac or VPS daemon serves registered clients over private authenticated HTTPS. Two isolated client homes and a real browser must read, reply, attach, recover an uncertain send after restart, and switch one client away without affecting the other or moving pending work to another workspace.

## Released clients must fail safely during an upgrade

Baseline IPC is 12 and clients require exact remote IPC compatibility. F01 uses protocol 13 because its new enum variants are rejected by older peers. The local host CLI probes compatibility before sending an authority request and reports an upgrade instruction without restarting the daemon. F01 does not add fields to every existing IPC envelope merely to reserve future shape. Each stage records mixed-version behavior, daemon/client installation order and fixture versions. Older clients must receive an actionable error rather than restart a remote host or fall back locally. Database migrations are additive; forward-fix after migration rather than guessing that an older binary can open a newer schema. Portable backup/restore must invalidate remote auth while retaining workspace ownership/recovery safeguards.

F01 requests only `mail_read`; later write grants require explicit approval. Pairings expire after ten minutes, at most sixteen remain pending, and five failed claim proofs lock a request. Ordinary credentials expire after ninety days. Separate cleanup verifiers remain after expiry or revocation so lost-acknowledgement retries can only deregister the original client.
