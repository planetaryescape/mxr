## S2 and S3 proof reuse

### S2 supports a bounded local-query demonstration

The retained proof at `docs/website-refresh/evidence/s2-runtime-proof.md` records an isolated fake-provider profile on published `mxr 0.6.156`, source/tag SHA `f39ae66578e3099e464967ab2f042e24b1ad8ec4`. The run synced 55 synthetic messages into each of two accounts, counted 55 per explicitly scoped account, returned one `newsletter` search result per account, and returned four eligible subscription sender buckets per account. Search result JSON identifies the matching account-specific message; subscription rows report READ-flag counts. The report explicitly says these are current local READ flags, not measured opens, and the fixture’s eligible buckets are not mailbox-wide real-world completeness.

I inspected only retained outputs with read-only `jq` selectors: both count files contain `{"query":"after:2000-01-01","count":55}`; each search file has one result with `read:false`; each per-account subscription file has four rows. The fixture at `/Users/bhekanik/.t3/worktrees/mxr/t3-726e9266/.cache/website-s2` measures 320 MiB. I did not invoke its runner or inspect secrets/config contents.

The current `count` and `subscriptions` handlers, subscription store query, and count renderer were checked in source. `crates/daemon/src/commands/count.rs#L7-L63`, `#L66-L82` still sends optional account scope and emits `{query,count}` JSON; `crates/daemon/src/commands/subscriptions.rs#L95-L129` still applies account scope, fetches the bounded set, and ranks that returned set. `crates/daemon/src/cli/mod.rs#L264-L279`, `#L1063-L1075` retain count’s account/group-by/format flags and subscriptions’ default `--limit 200`, account and rank flags. `crates/store/src/message.rs#L1093-L1168` still filters unsubscribable, spam/trash-excluded sender buckets, counts READ flags, and applies the limit after selecting one latest row per account/sender. These contract paths have no behavior change from the `0.6.156` source baseline; `cli/mod.rs` has unrelated later additions elsewhere. The retained outputs remain usable evidence of that past run and the same current command/result contract.

Reuse it only for this bounded claim: “In the retained synthetic run, mxr counted/search-matched local synced mail and ranked the eligible subscription rows separately within each selected account.” Do not say a current binary re-ran it, that all real newsletters were covered, or that a message was actually opened. A fresh proof against the release chosen for the website would require root to choose and run an isolated current fixture; this research did not do that.

### S3 supports a separate shared-draft and refusal demonstration

`docs/website-refresh/evidence/s3-shared-draft-proof.md` records a separate synthetic account and run. MCP read-only rejected draft creation; draft-only allowed local draft creation/update; the web client showed the same draft ID and revision-specific content; a prohibited send was rejected before provider dispatch, and scoped Sent search remained empty. The revision number was observed through MCP and associated with the web route/content, but the UI did not display the numeric revision. The proof says the refusal exercised `draft-only` while `allow_send=false`; it did not isolate the send-gate error alone.

This was deterministic MCP protocol replay, not model reasoning, default-agent behavior, or a rerun of S2. Its runtime was `0.6.156` at source baseline `cc00d4081bb5bd7875c39da4641ff95888817d80`; the report notes the Rust release source matched the `f39ae665` release, but today’s `main` is newer. Current request-source/profile and draft-send code supports the same described controls (`crates/daemon/src/handler/mod.rs#L2331-L2395`, `crates/daemon/src/handler/mutations.rs#L3513-L3539`, `#L3740-L3803`), but this is not current-runtime proof. Reuse the observation with its original version/ref, profile and account boundary. Do not combine S2 and S3 IDs or present them as one continuous account/session.

Together these packets demonstrate two composable surfaces, not a single observed end-to-end workflow. No invoice/attachment recipe has runtime proof in the retained packets; Rung 4 should keep the invoice recipe out unless root later captures a matching preview and resulting-state observation. The bounded fallback is the existing S2 local-search/subscription example plus the separately identified S3 shared-draft review.

- No recipient, attachment, article, remote-image, unsubscribe, or Marginalia outbound call was part of S2 or S3. Those boundaries above are source-derived, not demonstrated by these proofs.
