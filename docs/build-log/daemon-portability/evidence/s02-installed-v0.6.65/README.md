# S02 installed browser acceptance on v0.6.65

The browser journey used the published macOS v0.6.65 binary (SHA256 `86096ad9c869173c3fa6d69fcf0cac1547c94dc36ecd90e1f2ede2a1dea03e26`), release source `7cfb0c38cf10b975eb76232a3e53ad6eb3fc2f54`, tree `d8b8463eebbd1eaa4e5f47ed75d69b30cbadc531`. The embedded SPA was served by that binary; no development server or rebuild was used. The isolated profile contained synthetic fake mail only.

Two tabs opened one draft at revision 1. Editor B saved revision 2; editor A's stale update received 409 and retained its text and attachment through close/reopen. Recovery-only Discard removed the current private copy, preserved four earlier recovery files and their referenced bytes, and left the canonical winner unchanged. On a second draft, the actual IPC outage returned 503 while two canonical reads seven seconds apart remained unchanged. After reconnect, only explicit Retry saved the latest text. The actual request statuses are in [browser-updates](browser-updates.json); canonical state is in [the post-discard snapshot](canonical-after-discard.json), [the accepted retry](canonical-after-retry.json) and the two unchanged idle snapshots. [Discard verification](discard-verification.json) and the [final cleanup record](final-owned-cleanup.json) preserve the file/attachment outcome and process teardown. Selected screenshots show the conflict, Discard preview, IPC 503 and accepted Retry: [conflict](conflict-preserved.png), [Discard](recovery-discard-preview.png), [503](ipc503-preserved.png), [Retry](reconnect-retry-accepted.png).

The browser context also went offline and an owned bridge became unreachable. Both cases preserved the remembered recovery entry, and reopening succeeded after availability returned. Neither leg reached the loader catch: the availability guard handled both. Two typed outage regressions in the five-test `activeDrafts` suite cover the loader failure paths. These installed journeys therefore verify visible preservation and reopen after reconnection; they do not claim runtime execution of that catch. The recorded browser requests contain no compose send/schedule or explicit provider push/sync route; the isolated fake daemon did run its startup sync. The complete run through cleanup took 382.91 seconds.
