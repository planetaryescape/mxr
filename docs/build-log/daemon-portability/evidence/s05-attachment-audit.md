# Attachment operations still cross the boundary as host paths

Source: freshly fetched `origin/main` at `2c55a735e2b013910cb7222211fa8d6156d6204c`. Fast worker GPT-6-Luna/high performed a read-only audit; the parent checked the critical paths below. No runtime failure or S05 implementation is claimed. [Blob identities](s05-attachment-audit-2c55a735.json) support rechecking after S02/S03 deploy.

`Draft.attachments` is `Vec<PathBuf>` (`crates/core/src/types.rs:1604-1605`). Outbound helpers resolve and load those paths (`crates/outbound/src/attachments.rs:6-65`). With separate client and daemon filesystems, a supplied client path cannot identify daemon-owned bytes: it may be missing or name different content. S05 must cross that boundary with managed identities while preserving provider-local path resolution inside the daemon.

The current download handler materializes provider bytes into the daemon attachment directory, persists `local_path` in SQLite and returns `AttachmentFile { path }` (`crates/daemon/src/handler/mod.rs:3612-3661`, `crates/store/src/body.rs:123-141`). CLI download then calls `std::fs::copy` on that returned path on the client; CLI open dispatches `OpenAttachment` back to the daemon (`crates/daemon/src/commands/mutations/attachments.rs:219-268`). TUI overwrite confirmation checks the client filesystem, then submits that destination to IPC (`crates/tui/src/app/attachment_helpers.rs:108-163`). These operations need client-side byte writing/opening when the daemon is remote.

The web bridge already accepts upload bytes as base64, but writes them to a path derived from the compose file and returns that temporary path (`crates/web/src/lib.rs:1214-1238`). Message open/download routes still return the daemon's attachment-file response (`lib.rs:1447-1487`); the browser action reports the result in a toast (`apps/web/src/features/thread/AttachmentActions.tsx:22-37`). This is an existing byte-upload entry point, not a durable draft-owned attachment resource or browser byte-download contract.

IPC has a 16 MiB length-delimited JSON frame limit (`crates/protocol/src/codec.rs:5-20`). `materialize_attachment_capped` receives a complete provider byte vector before enforcing the cap on a new fetch (`crates/daemon/src/handler/mod.rs:3574-3575`, `3612-3620`). Its cached-file branch returns the existing size without applying that cap (`3597-3609`). Reusing it does not by itself bound transfer memory or enforce one end-to-end resource limit. No runtime threshold was measured.

Existing helpers worth preserving include outbound attachment resolution, private cache-file permissions, body attachment metadata, message-directory cleanup (`crates/daemon/src/message_deletion.rs:117`) and the compose-file helpers. Their current ownership is message/cache or compose-session based; do not infer draft-resource reference counting from them.

The registered MCP tool set at this SHA has draft tools but no attachment upload/download/open tool. S05's new reusable attachment capability must include MCP under the project's client-parity rule; this is not an optional capability decision. CLI, TUI and web should all consume the same daemon resource contract.

Before implementation, recheck the deployed S02 draft identity/revision changes and S03 preview/send binding. Keep interrupted-upload handling, finalized immutable IDs, referenced-resource retention and abandoned staging cleanup inside the attachment slice. The first transfer can restart after interruption; the blueprint does not require resumable chunking or a generic blob service. Test disjoint filesystems, exact byte identity, size rejection, incomplete upload, ownership rejection and cleanup of referenced versus abandoned bytes. This audit does not freeze those undeployed contracts.
