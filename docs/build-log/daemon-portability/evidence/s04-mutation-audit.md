# S04 recoverable mailbox actions: mutation audit

This is provisional discovery before S03 deployment. Source-code evidence is from freshly fetched `origin/main` at `80606f4833b651bf9b07975ddd49083d7cb2568a`; the research worktree HEAD when audited was `966d281cd92a5ef05dd710d82f83407c1afd059b`. The worktree source matched that main revision; its differences were research/build-log documentation. References below use the source SHA unless marked `@966d281`.

This audit is source-only. No builds, tests, provider calls, or credential use were performed. It describes checked code paths, not observed live-provider behavior. In particular, the fake-provider failure seam rejects before recording a mutation, so it cannot establish how any live provider behaves when acceptance occurs but the response is lost. Recommendations remain provisional until S03’s workspace, recovery-generation, and stable-caller contract is deployed.

## Findings

- No caller-retained operation key exists. Protocol mutation carries action/IDs/options; `Request::Mutation`/`StartMutationJob` have only command and optional `client_correlation_id` (`crates/daemon/src/protocol/types.rs@80606f4#L1009-L1029`, `#L2623-L2666`). The correlation ID only labels a partial-failure event (`crates/daemon/src/handler/mutations.rs#L494-L526`); `mutation_id` is generated randomly per execution and used for dedup/undo (`#L540-L552`, `#L603-L629`). `IpcMessage.id` is client request multiplexing and `source` is `ClientKind`, not stable caller identity (`protocol/types.rs#L469-L531`).
- Job acceptance is not recoverable by caller key. `start_mutation_job` creates random `job_id`, stores only status/progress/undo IDs/error/result, then spawns task (`handler/mutations.rs#L849-L887`; `protocol/types.rs#L2732-L2765`). List/get look up only that random job ID (`mutations.rs#L889-L911`). If `JobStarted` response is lost, no mapping from request to job exists; persisted job omits command and selection. Restart recovery is absent: task is only spawned at `#L881-L884`; no run-on-start recovery path was found. Progress/result persists only after each 100-item chunk, then terminal update (`#L914-L1065`).
- Two bounded stores are not operation receipts. Internal dedup is `(mutation_id, provider_message_id)`, with 24h expiry (`crates/store/migrations/040_mutation_dedup_log.sql@80606f4#L1-L36`); lookup does not check `expires_at`, insert records it, and hourly pruning removes expired rows (`crates/store/src/mutation_dedup.rs#L15-L71`; `crates/daemon/src/loops.rs#L2180-L2210`). Job rows are capped at 100 without terminal-status exception; on overflow an older active job can be pruned and later updates no-op (`handler/mutations.rs#L29-L35`, `#L1103-L1153`; `crates/store/src/mutation_jobs.rs#L69-L83`). Also, start proceeds after a job-persist warning (`mutations.rs#L849-L887`), so accepted work can lack durable job metadata if insert fails.
- Current outcome is aggregate, not per-item. `MutationResultData` and `JobProgress` have counts/accounts/results but no item outcome list (`protocol/types.rs#L2695-L2765`). Batch applies account-by-account, stops at first provider error, marks that snapshot uncertain and skips the failing/remainder of that account; it does not increment `failed` for this case (`handler/mutations.rs#L667-L836`, especially `#L732-L805`). A dedup row is recorded only after provider success; provider error leaves no row, and dedup persistence failure is warning-only (`#L1974-L2029`). The current paths therefore cannot distinguish a provider rejection-before-effect from acceptance followed by a lost/error response; fake failure rejects before recording (`crates/provider-fake/src/lib.rs@80606f4#L442-L501`).
- Partial/undo foundations exist but are not durable batch receipts: successful and potentially uncertain snapshots feed an undo record, written once after batch with 60s TTL (`handler/mutations.rs#L603-L629`; `crates/store/src/undo.rs#L118-L154`). Undo retains retryable failed snapshots under the same ID (`mutations.rs#L1375-L1405`). Tests cover same-process dedup and dedup-store expiry (`mutations.rs#L4526-L4597`; `crates/store/src/tests.rs#L3888-L3955`), aggregate multi-chunk job (405 archive items, chunk undo IDs) (`crates/daemon/src/handler/tests/mutations_and_delivery.rs@80606f4#L645-L710`), partial failure / uncertain undo (`.../stars.rs#L162-L198`), and cross-account partial counts (`mutations_and_delivery.rs#L1008-L1040`). No current acceptance seam covers replay after a dropped response or restart between item/chunk with persisted per-item receipts.
- Preview and selection seams: generic mutations resolve explicit/piped/search selection once, then use the same IDs for that invocation’s confirmation/request (`crates/daemon/src/commands/selection.rs@80606f4#L1-L13`, `#L100-L143`; `commands/mutations/helpers.rs#L382-L447`); a later dry-run/commit re-resolves and can drift. Places sweep has a one-time 10m preview token bound to scope/exact IDs, revalidates eligibility, and a per-chunk guard (`handler/places.rs#L759-L823`, `#L833-L953`), but consumes the token before job start (`#L925-L943`). Unsubscribe purge also consumes a one-time token, bound to scope/message set/method (`handler/mutations.rs#L3850-L3954`). Updates let-go hashes cut time plus sorted selected IDs and refuses changed selection (`updates_digest.rs@80606f4#L141-L175`; `updates.rs#L410-L447`). Web currently dedupes IDs client-side; generic resolver does not (`mailMutations.ts@80606f4#L39-L65`; `selection.rs#L100-L143`), so canonicalization must consciously define order/duplicate rules since partial-stop behavior is order sensitive.
- Client surfaces do not send durable IDs: web uses local ephemeral `op-${Date.now()}-${seq}` only for optimistic rows, then sends command and polls random job ID (`apps/web/src/features/mail-actions/mailMutations.ts@80606f4#L39-L65`; `mailMutationJobs.ts#L75-L150`). Web endpoint body accepts command/optional correlation ID and returns random `job_id` (`crates/web/src/routes_v6.rs#L885-L921`). CLI sync/job path likewise only polls returned job ID (`crates/daemon/src/commands/mutations/helpers.rs#L403-L459`; `commands/mutations/mod.rs#L116-L132`).

## Smallest direction

Follow the research sequencing: S04 depends on deployed S03 (`docs/implementation/daemon-portability/orchestration.md@966d281#L13-L20`). Then extend existing mutation/job persistence: accept a caller-retained operation ID; bind it to S03 scope/recovery/caller identity plus canonical validated command, exact reviewed selection, and parameters; persist unique ID plus payload fingerprint before spawn; exact replay resolves the existing job/receipt; changed payload conflicts. Link chunk-level internal mutation/undo IDs to the operation ID.

Persist per-item state/receipts and explicit unknown where provider outcome is inconclusive; do not blindly retry. Avoid treating current 100-job and 24h dedup retention as operation-ID retention. Reuse sweep/selection guards and make replay resolve an accepted operation before consuming a one-time preview token. Keep the S04 contract provisional until S03 deploys because scope, caller, and recovery identity are upstream.
